## 1. Purpose

The benefits logic tree shows the chain from design lever to measurable benefit before any number exists. It is agreed with Finance at G0 so that the method is not disputed at G2 when the numbers are. Every benefit in the business case must trace to a lever, a KPI, a baseline value and an owner.

## 2. Benefit categories

| Category | Definition | How valued |
|---|---|---|
| **Cash-releasing** | Reduces cost that would otherwise be incurred | £ at loaded rate; only counted if a budget line changes |
| **Capacity-releasing** | Frees colleague time; treatment decided post-G2 (SD-04) | FTE-equivalent; £ shown at both redeployment value and cost-avoidance value |
| **Risk and control** | Reduces loss, exceptions or regulatory exposure | Qualitative, plus £ where loss data allows |
| **Revenue-enabling** | Faster decisions retain or win business | Qualitative at G2; quantified only with Finance agreement |
| **Replacement cost avoidance** | Reduces build, test and run cost of the replacement | £ from Programme estimates |
| **Experience** | Colleague and customer | Non-financial KPIs |

## 5. Counting rules (agreed with Finance)

1. Capacity is counted once, at the role where it is released, net of any new activity the design adds to that role.
2. Capacity converts to cash only if SD-04 is decided as (a) and a budget line changes; otherwise reported as FTE-equivalent with a redeployment value.
3. Replacement cost avoidance uses the Programme's own estimates; this project does not estimate build cost.
4. Revenue-enabling benefits are described at G2 and quantified only if Finance agrees a method.
5. Baselines are frozen at G1 and re-measured at the same grain after each release.
6. Dis-benefits (e.g. Credit workload concentration on complex cases, training time) are recorded alongside benefits.
